一、它做什么，解决什么问题

CPA（CLIProxyAPI）用一份 config.yaml 管理几十到几百个上游凭据； sub2api 是网关，负责真正的调度与计费。两者的账号模型不通用， 手工搬运几百条凭据不现实。本工具就是这条搬运流水线。

14 项参数全覆盖

credentials、priority、concurrency、auto_pause_on_expired、proxy_id、请求头、冷却规则、Websockets、模型白名单等一次性迁移。

按域名分桶

同一上游的多个 KEY 互为备份、落进同一优先级桶；只有整桶不可用才降级到下一个域名。

健康度重排 已修

按 sub2api 实测的可调度率 60% + 活跃率 40% 重排优先级，分组内桶号唯一。

模型就高原则 已修

codex 与 openai 分开处理，代际门槛从上游源码反推，不写死版本号。

并发导入

建号 / 探活 / 定价三条链路都走线程池，worker 数可配且自动钳上限。

反测活

探活用自然语料，并给每个账号错开探活时刻，避免「全体同时探活」这一机器特征。

关于 CPA / CPAMP / sub2api 这三个项目都是第三方作品，本工具不修改它们。 所有调度与容灾的改进都落在本工具写入 sub2api 的数据上。

三、Docker 部署

部署模型是「VPS 只拉远程镜像」：本机改代码 → 推 GitHub → GitHub Actions 构建推 Docker Hub / GHCR → VPS 拉镜像运行。 所以 VPS 上不需要源码，只需要镜像和几个配置文件。

1拉取镜像

镜像名由你自己的环境变量决定，不是写死的。先在 .env 里设好：

# .env —— 镜像来源
DOCKERHUB_USERNAME=你的DockerHub用户名
DOCKERHUB_IMAGE=cpa2sub2api        # 可选，留空则用仓库名
docker pull $DOCKERHUB_USERNAME/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest
这一组变量同时决定 CI 往哪里推 GitHub 仓库里 Settings → Secrets and variables → Actions 要配置：
  • Variables：DOCKERHUB_USERNAME（与上面一致）、DOCKERHUB_IMAGE
  • Secrets：DOCKERHUB_TOKEN（Docker Hub 的 Access Token，不要填登录密码）
只配 DOCKERHUB_USERNAME 不配 token 也不会让构建失败 —— 那一处会安静跳过，只发 GHCR。
2准备配置文件

在部署根目录（如 /opt/deploy）放这些文件：

文件作用是否必需
.env连接信息与开关必需
config.yamlCPA / CPAMP 的产物，导入的源数据必需（或用 CPA_BASE_URL 在线拉）

nginx.conf反向代理本项目不需要（它不是 HTTP 服务）

2.1 .env 里本项目需要的项

# ── 必填 ──────────────────────────────────────────────
DOCKERHUB_USERNAME=你的用户名
DOCKERHUB_IMAGE=cpa2sub2api

# sub2api 管理地址。必须用服务名，不能写 127.0.0.1 ——
# 容器里的 127.0.0.1 是本容器自己，不是 sub2api。
# 端口用 sub2api 容器内监听的端口，不是宿主映射端口。
SUB2API_BASE_URL=http://sub2api:8080
SUB2API_ADMIN_KEY=你的管理员密钥

# ── 可选 ──────────────────────────────────────────────
# CPA 管理接口：本地没有 config.yaml 时用它在线拉
CPA_BASE_URL=http://cli-proxy-api:8317
CPA_MANAGEMENT_KEY=

# 代理兜底：复用同栈已有的 mihomo
FALLBACK_PROXY=http://mihomo:7890

# 并发（三项都会被硬性钳到 8）
IMPORT_WORKERS=4
TEST_PLAN_WORKERS=8
PRICING_WORKERS=8
两个最容易配错的地方 ① SUB2API_BASE_URL 与 FALLBACK_PROXY 在容器里 必须用服务名。写 127.0.0.1 指向的是容器自己。
② 端口要填容器内的。比如 sub2api 宿主映射是 127.0.0.1:8070→8080，容器间访问就该写 :8080， 写 8070 连不上。

本项目镜像自带 mihomo（代理内核 + 地理数据都打进镜像了）。所以代理不需要 额外的镜像、也不需要宿主机放任何 mihomo 文件 —— 同一个镜像起两个容器就够了： 一个跑 bootstrap-mihomo.sh 把配置物化进共享卷，一个跑 mihomo 本体。

为什么不直接用 mihomo 官方镜像 它基于 scratch：没有 shell、没有 python，展不开 config.template.yaml（要填订阅 URL 与 secret），连 bootstrap 脚本都跑不起来。 而部署约束是「VPS 只拉镜像 + 只上传三个配置文件」，宿主机上不能预置配置 —— 所以由本镜像兼任 init 与代理两个角色。 实测该二进制是 Go 静态编译（不 link musl 运行库），搬到 Debian 基座上照跑： mihomo -v → v1.19.31，-t 语法检查 rc=0。
3接入 compose

本项目服务通过服务名复用同栈的 mihomo： 

  cpa2sub2api:
    image: ${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest
    pull_policy: always          # 见下方说明，别用默认的 missing
    container_name: cpa2sub2api
    restart: "no"                # 运维工具，跑完即退

    env_file: [.env]

    environment:
      SUB2API_BASE_URL: "${SUB2API_BASE_URL:-http://sub2api:8080}"
      SUB2API_ADMIN_KEY: "${SUB2API_ADMIN_KEY:-}"
      CPA_BASE_URL: "${CPA_BASE_URL:-http://cli-proxy-api:8317}"
      CPA_MANAGEMENT_KEY: "${CPA_MANAGEMENT_KEY:-}"
      FALLBACK_PROXY: "${FALLBACK_PROXY:-http://mihomo:7890}"
      TZ: "Asia/Shanghai"

    volumes:
      # 单文件挂载：挂整个 /opt/deploy 等于把 .env、secrets/ 一起递给它
      - ./config.yaml:/app/config.yaml:ro,Z
      - cpa2sub2api-out:/app/out:Z

    # 它持有 sub2api 管理员密钥且能批量建号/改号，收紧权限
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]

    networks:
      - sub2api-network    # 访问 sub2api
      - default            # 访问 mihomo / cli-proxy-api

    depends_on:
      # 只等「起来了」，不等「健康」—— mihomo 节点全挂时会因出不去网
      # 而报 unhealthy，用 service_healthy 会让本工具永远起不来
      sub2api:  { condition: service_started }
      mihomo:   { condition: service_started }
为什么必须写 pull_policy: always compose 的默认策略是 missing：只看本地有没有同名 tag， 不比对 registry 上的 digest。所以镜像推了新的 :latest， docker compose up -d 也会静默继续用旧镜像 —— 这正是「自动更新不生效」的直接原因。
4启动并自动同步

容器起来就会自动把 config.yaml 同步进 sub2api，跑完即退。 你原来那条命令链加一步即可，不需要额外手动执行任何 py 命令： 

docker-compose down && docker-compose pull && docker-compose up -d && docker-compose logs --tail=180
它是怎么自动跑的 镜像的默认命令是 entrypoint.sh，它执行 一键导入.py（非交互入口）。所以 up -d 启动本容器 = 执行一次同步；配合 restart: "no"，同步完就退出，不会常驻。

以前默认命令是 python tool.py（交互式菜单）， 容器里没有 TTY 就立刻 EOF 退出、什么都不做 —— 看起来 up -d 成功、 实际一次都没同步，必须人工 docker compose run 才有效果。现已改正。

同步是幂等的

重复执行不会重复建号：账号名含内容指纹（sha1(api_key|base_url) 前 8 位）， 已存在的走差异同步，只更新真正变化的字段。所以每次 up -d 都可以放心让它跑一遍。

想要定时重复同步

两种方式，按你的部署习惯选：

方式做法适用
容器内循环 在 .env 里设 RUN_INTERVAL_SECONDS=3600， 并把 compose 的 restart 改成 unless-stopped 希望配置全在 compose 里，不碰宿主机
宿主 cron 加一条 crontab，定时执行 docker-compose run --rm cpa2sub2api 想和宿主上其它定时任务统一管理 
# 方式一：容器内循环（.env）
RUN_INTERVAL_SECONDS=3600
# 同时把 compose 里 cpa2sub2api 的 restart 改成 unless-stopped

# 方式二：宿主 cron（crontab -e）
0 3 * * * cd /opt/deploy && docker-compose run --rm cpa2sub2api >> /var/log/cpa2sub2api.log 2>&1
自动化的一个副作用，决定前请先权衡 每次导入都会按 sub2api 的实测健康度重算优先级 （可调度率 ×0.6 + 活跃率 ×0.4），并覆盖线上值。

也就是说：你在 sub2api 后台手工调整过的优先级会被算法值覆盖。
  • 不手工干预 → 定时同步很合适，坏站会被自动降级
  • 会手工干预 → 建议保持「每次 up -d 同步一次」，不要叠定时任务

临时/手动执行（可选）

不想重新起整个栈时，也可以单独跑一次：

# 只跑一次同步（不碰其它服务）
docker compose run --rm cpa2sub2api

# 交互菜单：分步操作、回滚、推送定价
docker compose run --rm cpa2sub2api python run.py

# 空跑预览：只生成对照表，不写 sub2api
docker compose run --rm cpa2sub2api python 一键导入.py --dry-run

# 查看产物（卷名前缀 = compose 项目名，通常是部署根目录名）
docker volume ls | grep cpa2sub2api-out
docker run --rm -v "$(basename "$PWD")_cpa2sub2api-out":/o alpine ls -l /o

4.5 config.yaml 逐字段说明 新增

这一节回答的是「CPA 的 config.yaml 里每个字段是什么意思、本工具怎么用它」。 与 4.1–4.4 的关系：4.1–4.4 讲的是本工具的配置（.env）， 这一节讲的是输入数据的格式。

先分清两个同名文件 config.yaml 这个名字在本项目里指两样东西，很容易混淆：
· CPA 的 config.yaml —— 输入。CPA / CPAMP 生成的配置，里面有你要导入的全部上游凭据。
· 本项目的 config.yaml.example —— 只是模板示意，不参与运行。
本工具读的是前者，容器里挂在 /app/config.yaml（只读）。

config.yaml 里与本工具相关的顶层段一共 6 个，各自对应 sub2api 的一个渠道：

顶层段名平台渠道分组协议
claude-api-keyanthropicCPA-ClaudeAnthropic Messages
codex-api-keyopenaiCPA-Codex强制 Responses
openai-compatibilityopenaiCPA-OpenAI强制 Chat Completions
gemini-api-keygeminiCPA-GeminiGemini 原生
interactions-api-keygeminiCPA-Gemini同 gemini
xai-api-keygrokCPA-Grok同 codex 结构

凭据级字段（每个段下面 - 开头的条目）——这些是最需要看明白的：

字段含义本工具怎么处理
api-key 上游密钥明文 原样迁到 sub2api 的 credentials.api_key。必填——为空会被跳过， 并记进「丢弃说明」让你看得见（以前是无声丢弃）
base-url 上游端点 迁到 credentials.base_url；同时决定归组用的域名
priority 选择偏好，数值越大越优先 映射成 sub2api 的桶号（数值越小越优先，方向相反）。 同一渠道同一域名的多个 KEY 会拿到同一个桶号，互为备份
weight 加权轮询份额。省略=1，非正数=排除 sub2api 没有对应字段。默认策略是「降到队尾」（可逆）， 而不是建成停用（不可逆）。见 4.3 的 WEIGHT_ZERO_POLICY
prefix 模型命名空间前缀，如 ANT/ 只进备注（sub2api 侧靠分组区分渠道），不参与调度
models 该凭据提供的模型列表（含 alias 别名） 经「就高原则」筛成 sub2api 的 model_mapping 白名单，见 7.4
excluded-models 该凭据排除的模型 从白名单里减掉（sub2api 没有黑名单字段）。 减空了会写一个占位项，防止「空表=放行全部」的反向事故
headers 附加请求头 迁到 credentials.header_overrides。 值以 $ 开头的是动态头（从下游请求复制同名头）， sub2api 只能存静态值，所以整条丢弃并记进「丢弃说明」。 另外黑名单（authorization / x-api-key / cookie 等 30 条） 里的头会被剔除——带了服务端会 400 拒掉整条账号
proxy-url 该凭据走哪个代理 迁到顶层 proxy_id（sub2api 的代理是独立实体， 本工具会按 URL 去重建/复用）。同域名的其它条目会自动跟进
request-scoped-errors 自定义上游错误分类规则（status / match / action） 迁到 credentials.temp_unschedulable_rules。 只有 *-and-cooldown 类 action 会建规则； match-regexr（正则）无法迁移，因为 sub2api 只支持子串匹配
cloak 请求伪装（改 system 提示、注入计费头、混淆敏感词） 写入 extra.cloak，但 sub2api 网关层没有消费逻辑， 写了不生效。已在备注里标注
fingerprint-profile 选 Claude Code 请求指纹 只置 extra.enable_tls_fingerprint=true。 模板绑定需要人工做：sub2api 的 TLS 指纹只对 Anthropic OAuth / setup-token 账号生效，而本工具导入的全是 api_key 账号
websockets 启用 Responses API websocket 传输 迁到 extra.openai_ws_enabled
alpha-search xAI 搜索能力 迁到 credentials.openai_capabilities（xai 段强制 false）
disabled 该 provider 是否关闭（只在 openai-compatibility 有） 建成 status=inactive。但仍然会被探活—— 探活证明可用后会重新启用，见 4.3 的 REVIVE_PROVEN_INACTIVE
api-key-entries provider 下挂的多个 key（只在 openai-compatibility 有） 每个 entry 展成一条独立账号。 entry 级只有 3 个字段：api-key / weight / proxy-url ——priority 是 provider 级的，所以同一 provider 下的所有 key 共用同一个桶号
rebuild-mid-system-message 把 role=system 的中途消息提到顶层 无 sub2api 等价物，只记进备注

顶层全局字段里，本工具真正会读的只有一处：

字段本工具怎么用
routing.strategy 决定 weight<=0 是否等于停用。 CPA 只在 weighted-round-robin 下排除零权重凭据； 其它策略（round-robin / fill-first）下零权重照常参与调度， 这时本工具不会降级它——否则等于凭空改变调度顺序
其余全局项（port / tls / debug / cloak 全局开关等） 本工具不读取、不迁移。它们作用于 CPA 自己那一侧的行为
最小可用的 config.yaml 长什么样 只有两段是必须的：至少一个 *-api-key 段，每段里至少一个带 api-key 和 base-url 的条目。下面的骨架可以直接复制改。 
# CPA 的 config.yaml —— 最小可用骨架
# 注意：这是 CPA 那边生成的配置，不是本工具的配置（本工具是 .env）

port: 8317

# 决定 weight<=0 是否等于停用。本工具会读这一项。
routing:
  strategy: weighted-round-robin

# ── Claude 渠道 ──────────────────────────────────────
claude-api-key:
  - api-key: "sk-ant-你的密钥"
    base-url: "https://上游.example.com"
    prefix: "ANT"
    priority: 100          # 数值越大越优先（与 sub2api 相反，本工具会翻转）
    weight: 1
    models:
      - name: "claude-opus-5"
        alias: "claude-opus-5"
    headers:
      user-agent: "claude-cli/2.1.258 (external, cli)"
      x-app: "cli"

# ── Codex 渠道（走 Responses 协议）──────────────────
codex-api-key:
  - api-key: "sk-你的密钥"
    base-url: "https://上游.example.com/v1"
    prefix: "CDX"
    priority: 100
    models:

5.5 代理本体：同镜像起两个容器

本项目镜像里已经装了 mihomo 二进制与地理数据，所以 compose 里只需两个服务， 都用同一个镜像，靠 entrypoint 区分角色：

同一个 mihomo，两个项目都能用 整栈上通常还跑着 upstream-importer，而它的镜像里也打了同一份 mihomo。实测两者的 mihomo 完全同源：二进制 md5 相同、mihomo -v 都是 v1.19.31、healthcheck.sh 与 bootstrap-mihomo.sh 的 md5 也相同、路径都是 /usr/local/bin/mihomo。 所以代理服务用哪个镜像起都行，所以这里写成了变量： 
image: "${MIHOMO_IMAGE:-${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest}"
不设 MIHOMO_IMAGE 就用本项目镜像；想在整栈里改用 importer 的， 在部署根 .env 里设： 
MIHOMO_IMAGE=swhesong/cpa-upstream-importer:latest
两个服务（mihomo 与 mihomo-init）必须用同一个镜像 —— 它们是同一个能力的两半（前者物化配置进卷、后者读卷跑代理）。
消费方怎么指向这个代理
cli-proxy-api（CPA 本体） config.yaml 里 proxy-url: "http://mihomo:7890"
cpa2sub2api（本项目） FALLBACK_PROXY=${FALLBACK_PROXY:-http://mihomo:7890}
upstream-importer DRIFT_PROXY / MIHOMO_URL，代码回落表也是 http://mihomo:7890

三者都在 default 网络上，靠服务名 mihomo 直连容器 IP， 不经过宿主端口映射 —— 所以宿主端口冲突不影响它们。

宿主 7890 常被占 本机若装着 Clash / Mihomo 客户端，它自己就占着 7890，up -d 会直接 失败（bind: Only one usage of each socket address）。 宿主侧端口是可覆盖的，在 .env 里改： 
# 宿主端口冲突时改这两个（容器内端口不能动）
MIHOMO_HTTP_PORT=7890
MIHOMO_API_PORT=9090
容器内端口必须保持 7890/9090 —— 它要与 config.yaml 里的 proxy-url: http://mihomo:7890 以及 healthcheck.sh 的探测端口一致。改宿主侧即可，容器间通信走服务名，不受影响。 
  mihomo-init:              # 一次性：把配置物化进共享卷
    image: "${MIHOMO_IMAGE:-${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest}"
    pull_policy: always
    restart: "no"
    user: "0:0"             # 卷首次由 Docker 以 root 建出，uid 1000 写不进去
    entrypoint: ["/bin/sh", "/app/mihomo-manager/bootstrap-mihomo.sh"]
    environment:
      MIHOMO_SUB_WOG:  "${MIHOMO_SUB_WOG}"
      MIHOMO_SUB_WOGB: "${MIHOMO_SUB_WOGB}"
      MIHOMO_SECRET:   "${MIHOMO_SECRET:-}"
      MIHOMO_TARGET_DIR: "/root/.config/mihomo"
    volumes:
      - mihomo-data:/root/.config/mihomo:Z

  mihomo:                   # 长驻：同一个镜像，换成 mihomo 本体
    image: "${MIHOMO_IMAGE:-${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest}"
    pull_policy: always
    container_name: mihomo
    restart: unless-stopped
    user: "0:0"             # 要往配置目录写 cache.db
    entrypoint: ["mihomo"]  # 两个镜像都在 /usr/local/bin，写名字即可
    command: ["-d", "/root/.config/mihomo"]
    depends_on:
      mihomo-init: { condition: service_completed_successfully }
    ports:
      # 宿主侧可覆盖（本机已有代理客户端时会占着 7890）；
      # 容器内端口不能动 —— 要与 proxy-url 和 healthcheck 一致
      - "${MIHOMO_BIND:-127.0.0.1}:${MIHOMO_HTTP_PORT:-7890}:7890"
      - "${MIHOMO_BIND:-127.0.0.1}:${MIHOMO_API_PORT:-9090}:9090"
    volumes:
      - mihomo-data:/root/.config/mihomo:Z
    healthcheck:
      # 见 5.6：脚本不只会判活，还会把出口降级到 DIRECT
      test: ["CMD", "sh", "/root/.config/mihomo/healthcheck.sh"]
      interval: 60s
      timeout: 40s
      retries: 3
      start_period: 40s
三个容易踩的点
  • 两个服务必须挂同一个卷，否则 init 写的配置本体读不到；
  • 两个服务都写 user: "0:0" —— 命名卷首次由 Docker 以 root 建出， uid 1000 往里写会 Permission denied；
  • 卷要用 :Z，CentOS 9 默认 SELinux enforcing，不加标签容器读不到。

5.6 出口真的废了会自动降级 容易忽略

机场节点全挂时，mihomo 进程本身活得好好的：端口在听、API 有响应、 AUTO 组里还列着几十个节点名字。日志里看不出任何异常，但所有配了 proxy-url 的上游都会走进这个没有出口的代理里排队到超时 —— 表面现象是上游 502/524。

光把容器标成 unhealthy 救不回来：restart: unless-stopped 不会因为 unhealthy 重启容器，而且健康检查本身改不了选路。 所以健康检查调的是 healthcheck.sh，它会：

  1. 查 9090 API 是否响应（没响应 = 进程坏了，退出 1 让 docker 重启）；
  2. 清点 AUTO 组节点数（只用于日志，节点数不是可用性判据）；
  3. 真正经 7890 出一次网。通 → 若当前在 DIRECT 就切回 AUTO；
  4. 不通 → 调 PUT /proxies/PROXY {"name":"DIRECT"} 降级， 再试直连；直连通就保持健康（降级不算失败），都不通才报 unhealthy。
# 手动跑一次（排查用；它真的会切组）
docker compose exec mihomo sh /root/.config/mihomo/healthcheck.sh; echo rc=$?

# 正常时的两种输出：
#   [healthcheck] 出口已恢复（AUTO 组 59 个节点），切回 AUTO
#   [healthcheck] 代理出口不可用（AUTO 节点 59 个，探测 ... 失败），降级 DIRECT
#   [healthcheck] 直连可用，容器保持健康（流量已走 DIRECT）

# 看 compose 记下的最近几次检查结果
docker inspect --format '{{range .State.Health.Log}}exit={{.ExitCode}} {{.Output}}{{"\n"}}{{end}}' mihomo
脚本要在两种基座里都能跑 mihomo 官方镜像是 busybox，本项目镜像是 Debian slim —— 两者可用的命令不同。 Debian 里装了 busybox 也不会自动出现 /usr/bin/nc （实测：have busybox，MISS nc），而切换出口是 PUT，busybox 的 wget 只能发 GET/POST， 必须有 nc。所以脚本对 nc / wget 各做一次"命令探测 + 回退到 busybox <applet>"，同一份脚本两边通用。 两个工具都找不到时它会直接说"本镜像缺工具"，不会伪装成出口故障。

七、工作原理

7.1 优先级是「桶号」，不是权重

CPA 和 sub2api 都按优先级严格分桶：只调度优先级最优的那一桶，同桶内再按负载选号。所以优先级数值不是「权重」，而是「层级」。

7.2 健康度重排

比例的分母：只算「已导入的 KEY」，不算「KEY 总数」

这一条决定了扩容时老域名会不会被无故降级，是实际会踩到的点。

需求文档没有定义分母 原文只写「可调度比例×60% ＋ 活跃比例×40%」。两种取法都符合字面要求， 但只有「已导入数」满足另一条约束：原有的 KEY 和上游不能因为扩容而被降级。
整个域名都是新增时给中位分 0.5 一条都没导入过的域名没有任何实测数据。给 0.5 而不是 0： 既不因「查无记录」被打到队尾（新站可能很好）， 也不凭空排到已验证的健康站前面。对应 load_factor = 4。

7.3 三层容灾链路

7.4 模型「就高原则」 已修

类型规则
gemini只选带 pro 的最高编号，保留该版本全部变体
claude只选当代，保留全部档位（opus / sonnet / haiku）
codex单族：只保留当代 gpt 系列全部模型名
openai多族：每一族各取最高级，允许多族并存
其他原样保留（grok 等）
低档模型一律不勾选

名字里带 mini / flash / fast 的排除， 四条路径（gemini / claude / codex / openai）统一执行。过滤后一个不剩时保留原列表并出声 —— 白名单为空等于该账号退出调度，比留几个低档模型更糟。

注意 claude 的 haiku 不算低档：它与 opus / sonnet 是同代不同档位， 按「同等级系列全部勾选」应当保留。低档判据只认那三个词。

连通性探测：最新代打不通时的兜底

上游声明了 gpt-6 不等于真的能调。模型目录是站方自己填的， 常有「列了但调不通」的情况。开启探测后按代际实发请求验证，据结果分三种处理。

成本：231 个账号 → 49 个探测单元 → 约 30 秒

不逐模型探测，那样会打上千个请求。按 (段, 域名) 去重， 每个单元最多 2 个请求（最新代 + 次最新代）。同一站的多个 KEY 共享判定结果 —— 它们打的是同一个上游，模型可用性一致。

结果缓存 6 小时，重跑命中缓存 0 秒。关闭探测时零开销，行为与不带该功能完全一致。

MODEL_PROBE_ENABLED=true       # 默认开启，设 false 完全跳过
MODEL_PROBE_WORKERS=8          # 并发
MODEL_PROBE_CACHE_TTL=21600    # 缓存秒数（6 小时）
端点拼接必须与 CPA 源码一致

探测用的 URL 按 CPA 自己的拼法构造：baseURL 原样 加各平台端点后缀，不剥离尾部 /v1。CPA 的 base-url 是声明式配置， 末尾的 /v1 是配置的一部分。

段CPA 源码的拼法
claude-api-keybaseURL + "/v1/messages"
codex-api-keyTrimSuffix(baseURL,"/") + "/responses"
openai-compatibilityTrimSuffix(baseURL,"/") + "/chat/completions"
gemini-api-keybaseURL + "/v1beta/models/{model}:generateContent"

自行剥离 /v1 会拼出 .../v1/v1/messages， 拿到 nginx 的 404 HTML 页，把「端点拼错」误判成「上游不通」。

判「通」不能只看 200

很多中转站有 catch-all 路由：错误的端点也返回 200，但响应体是 HTML 前端页而不是 LLM 响应。必须校验响应体形态 （id/choices/content 等字段），否则会得到大量假阳性。

400 / 422 也算通：请求到了模型、只是参数被挑刺， 说明这个模型确实存在且可路由。404 model_not_found、 503 No available channel 才是真不通。

7.5 反测活

两层措施：

  • 语料：中英双语、覆盖多种日常话题，随机抽取。不用 「test」「你好」「你是什么模型」这类教科书特征。 2026-09-19 补齐 探活计划那条链路本来就有 30 条语料池，但探测链路 （model_probe.py，导入时用来判模型通不通）三处都硬写着 "hi" —— 那是个常量，站方按「请求体恒为 hi 且 max_tokens=1」就能一眼认出探活流量，比措辞本身更好认。 现已改成与探活同类的短句池（中英各 5 条）随机抽取， 仍保持 max_tokens=1 的极低消耗。
  • 时刻错开 新增： 给每个账号派生一个稳定的分钟偏移（用账号名哈希，保证同一账号每次 得到同一偏移、不同账号之间散开）。实测 100 个账号会散到 29/30 种可能的时刻。
两条链路的语料为什么是两个池 探活计划（sub2api 定时任务）用的是 30 条较长句子，因为它要模型 真的把话答完才算成功；探测链路只判「这一代模型在这个站上认不认」， 请求体越小越不容易被限流，所以用短句。两者都避开教科书特征词， 但长度诉求相反 —— 合成一个池反而两头不讨好。

八、故障排查

8.0 先把日志打开（需求第 8 条）

遇到问题时，第一件事是打开 DEBUG 日志和落盘。默认级别下你看到的是 「阶段进度 + 统计 + 结论」，而故障现场在那些没有打印出来的分支里 —— 重试、降级、被丢弃的字段、原本被静默吞掉的异常。

变量默认说明
LOG_LEVELINFO DEBUG / INFO / WARNING / ERROR / CRITICAL。 排查时设 DEBUG
LOG_TO_FILEfalse 写 out/logs/run-<时间戳>.log。 排查时建议打开：容器里 docker logs 通常只剩最后几十行
为什么落盘文件一律记 DEBUG 即使你把 LOG_LEVEL 留在 INFO（为了屏幕干净）， 文件里仍然有完整的 DEBUG 细节。这是刻意的：屏幕要能看清结论， 文件要能事后追查 —— 两者的诉求正好相反。 
# 一次排查运行的完整姿势（三处都打开）

# 1) 在部署根的 .env 里加：
LOG_LEVEL=DEBUG
LOG_TO_FILE=1

# 2) 重跑（容器方式）
docker compose run --rm cpa2sub2api

# 3) 把日志和产物一起取出来
docker compose cp cpa2sub2api:/app/out/logs ./logs-debug
ls -la ./logs-debug

# 本机直接跑（不经容器）：
LOG_LEVEL=DEBUG LOG_TO_FILE=1 python 一键导入.py

日志里该看什么——按"最常问的四个问题"对照：

你想知道日志里搜什么说明
代理兜底到底试没试？ 代理兜底失败 / [代理兜底] 直连失败后是否走过代理、代理那一步为什么没成。 以前这一步完全静默，日志看起来像根本没兜底
探活计划为什么没挂上？ 取账号 … 的探活计划失败 区分「查不到」与「查到了但没成功」—— 后者才会启用停用账号，前者不会
为什么账号没走代理（直连了）？ 重查代理列表也失败 / 相关账号将直连 建代理撞重名后重查失败 → 拿不到 proxy_id → 静默直连。这正是「前端 mihomo 链接失败」的一种成因
我的配置到底生效了没有？ 不是整数，已忽略 / 不是有效级别 / 读取 设置.json 失败 写错类型的变量会被明确点名并说出退回了什么， 而不是默默沿用默认值
上游常量跟上版本了吗？ 漂移诊断失败 出现即表示没能检查 SECTION_MAP 等是否与上游一致 （以前这种失败会被当成「检查通过」）
要被支持的两种失败必须能分开 日志改造的一个原则：「没做成」和「没检查」不能长得一样。 以前的 except: pass 让两者都表现为"安静地过去了"， 运维据此只能怀疑自己。现在每一处静默降级都留下了带异常类型与位置的记录。

8.1 sub2api 的 IP 管理页显示「链接失败」

可能性怎么查
AUTO 组 0 节点 curl .../proxies/AUTO | jq '.all|length' 为 0。查订阅是否拉到、filter 是否把节点全筛掉
allow-lan: false mihomo 只接受来自 127.0.0.1 的连接，容器间访问会被拒。bind-address 不改变这一点
不在同一 Docker 网络 http://mihomo:7890 解析不到。跨 compose 项目的 default 是不同的网络

8.2 只调用高优先级上游，低优先级一次都不试

这是最典型的「看起来在轮循、实际死锁」故障。真实成因是凭据级错误被当成非重试错误：

本工具的对策（已修）：

  1. 域名级冷却：402「预算池耗尽」是整个上游层面的状态 （同一站的所有 KEY 共用同一个池子），不是单个 KEY 的毛病。 本工具给这类错误码下发更长（180 分钟）、关键词更特异的冷却规则， 避免在同一池子里逐个 KEY 空撞。
  2. 分组内唯一桶号：保证「整桶挂掉才降级」真的能降级。 编号范围是分组内 —— sub2api 选号按 group_id 取候选， 跨分组的桶号之间没有可比性，所以各组都从 10 起。
  3. 桶内冗余：同域名多 KEY 同桶轮循，一个被冷却后请求轮到同桶其它 KEY。

8.3 报 503 No available accounts 且提示分组权限

这不是本工具的问题 this group only allows Claude Code clients 说明该上游站点只接受 Claude Code 客户端。 需要在 CPA 侧给对应条目配好伪装请求头（user-agent / anthropic-beta / originator）， 与账号本身能否调用无关。

8.4 报 400 invalid codex request

同样与账号无关：该凭据的自定义模型列表里可能含不存在于上游的模型名， 或协议模式（responses / chat_completions）与上游不匹配。 用菜单里的「测试」确认连通性，再看 out/对照表.md 的放行模型是否合理。

8.5 报 524 origin_response_timeout

Cloudflare 的回源超时是 120 秒且无法从源站侧延长 （nginx 的 proxy_read_timeout 对它无效）。 一旦超时 CF 直接返回 524，此时源站其实还在正常重试。 对策是压缩单次请求的上游尝试预算： 

# CPA 的 config.yaml（全局段）
max-retry-credentials: 4     # 12 → 4
max-retry-interval: 2        # 8 → 2

# 最坏耗时 ≈ 4 ×（连接+首字节）+ 3 × 2 秒  ≈ 30 秒以内
# 对 120 秒窗口留足余量

8.6 报 empty or malformed response (HTTP 200) 且 0 个 SSE 事件

流式引导没缓冲的话，网关在还没确认上游会吐 token 时就先提交了 200 OK + text/event-stream 响应头。 此后若上游失败，网关已经没有退路——响应头发出去了，不能改 5xx、 也不能换凭据。唯一结果就是「语法合法但一个事件都没有」的 200。 

# CPA 的 config.yaml
codex:
  stream-bootstrap-buffering: true   # false → true
streaming:
  bootstrap-retries: 3               # 1 → 3

8.9 CPA 与 CPAMP 的五个密钥，别再搞混

  • 让 CPAMP 读到 CPA 的账号数据 → 用 ⑤（且要与 ① 匹配）

8.10 面板登不上：重置密钥（唯一有效的方法）

源码里写得明确（bootstrap/service.go）：

// 数据库里已有凭据就直接返回 —— 不再读 secrets 文件
if _, ok, err := st.LoadAdminCredential(ctx); err != nil || ok {
    return false, "", err
}
adminKey := cfg.AdminKey   // 只有首次启动才读文件

即：面板密钥只在第一次启动时确定，之后改文件一律无效。 想换只能用 reset-admin-key（它直接改写 SQLite）。 

cd /opt/deploy

# ① 先停 CPAMP，避免 SQLite 被占用
docker compose stop cpa-manager-plus

# ② 重置（不加 --admin-key 则自动生成随机密钥并打印）
docker compose run --rm --entrypoint cpa-manager-plus cpa-manager-plus \
  reset-admin-key --db-path /data/usage.sqlite

# 输出形如：
#   CPA Manager Plus admin key reset.
#   New admin key: xxxxxxxx...
#   Save this value now. It will not be shown again.

# ③ 启动，用它登录面板
docker compose start cpa-manager-plus
参数说明（源码 adminreset/command.go）
  • --admin-key VALUE　指定新密钥
  • --admin-key-file PATH　从文件读（不能与上面同用）
  • --db-path PATH　SQLite 路径；不传则读配置
  • 都不传 → 自动生成并打印，只显示一次

8.11 被自己的 IP 封禁：403 而不是 401

改密钥时很容易触发。CPA 源码里有两个常量：

const maxFailures = 5
const banDuration = 30 * time.Minute

认证失败累计 5 次 → 该 IP 封禁 30 分钟 → 之后所有请求返回 403，包括用对密钥的。

状态码CPA 源码里的含义
401missing management key / invalid management key —— 密钥不对
403IP banned ... / remote management disabled / key not set

只看状态码分不出 403 的具体原因，必须看响应体：

curl -s -i -H "Authorization: Bearer $KEY" \
  http://127.0.0.1:8317/v0/management/get-auth-status | head -20

# 看到这个就是被封了：
#   {"error":"IP banned due to too many failed attempts. Try again in 26m10s"}

解除方法（失败计数在内存里，重启即清空）：

cd /opt/deploy

# 关键顺序：先停 CPAMP，否则它会持续重试、不断延长封禁
docker compose stop cpa-manager-plus
docker compose restart cli-proxy-api
sleep 8

# 确认已解封（应返回 401，而不是 403）
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $(cat secrets/cpa_management_key)" \
  http://127.0.0.1:8317/v0/management/get-auth-status

docker compose start cpa-manager-plus
为什么必须"先停 CPAMP" CPAMP 在后台不断重试连接 CPA。CPA 重启的那十几秒里这些重试全部失败 —— 攒够 5 次立刻又把你封 30 分钟。顺序不能反。

8.12 secret-key 要的是哈希，不是明文

config.yaml 的 remote-management.secret-key 期望 bcrypt 哈希（$2a$10$ 开头，60 字符）。 写明文进去 → 认证彻底失效；哈希不可逆，只能从备份还原。

写哈希前必须校验 这个坑实际踩过：HASH=$(docker compose exec ... python3 ...) 在容器缺 bcrypt 时不会报错，而是把 OCI runtime exec failed... 赋给 HASH。 写进 config.yaml 后认证即失效。 
# 生成后立刻校验，不合格就别往下走
echo "HASH 长度: ${#HASH}"
case "$HASH" in
  \$2*) [ ${#HASH} -ge 59 ] && echo "OK" || echo "长度异常，中止" ;;
  *)    echo "不是 bcrypt 哈希，中止" ;;
esac

十、站方只认特定客户端：怎么让导入后的路由等价于直连

这是需求第 2 条⑴要解决的核心问题，也是实际最常见的「明明能用却报错」： 同一个上游，直接填进 cc-switch 能跑通，经 CPA / sub2api 中转就报 503 No available accounts（有时附带一句 this group only allows ...）。

为什么直连可以、中转不行 区别不在密钥、不在地址，在请求头。这类站点（多是中转/聚合站） 会校验客户端形态，只放行特定客户端的请求特征： User-Agent 是不是 claude-cli/…、 有没有 x-app: cli、anthropic-beta 带的标记对不对。 cc-switch 直连时，这些头由 Claude Code / Codex 客户端自己发出去，所以正常； 一旦走中转，发出请求的变成了网关，头就没了。

10.1 本工具现在怎么做

原来的实现是纯被动搬运：CPA 的 config.yaml 里写了 headers 就搬过去， 没写就什么都不带。问题在于——靠 CPA 默认伪装跑通的站点，config.yaml 里往往根本没写这些头， 于是导入 sub2api 后请求形态退化，站点就不认了。

现在改为「搬运 + 补缺」：把 CPA 里已有的头原样搬过去， 再把 CPA 没给、但客户端形态必需的头补齐。只补缺，绝不覆盖你显式配的值。

平台补入的客户端头
anthropic
Claude 渠道		 user-agent: claude-cli/2.1.258 (external, cli)、x-app: cli、 anthropic-dangerous-direct-browser-access: true、 x-stainless-* 六项、anthropic-beta
openai
Codex / OpenAI 渠道		 user-agent: codex_cli_rs/…、originator: codex_cli_rs
gemini user-agent: GeminiCLI/…、x-goog-api-client、accept
这套头的来源不是拍脑袋 它照抄的是 sub2api 自己内置的客户端伪装常量 （backend/internal/pkg/claude/constants.go 的 DefaultHeaders 与 beta 族）。所以补出来的形态与 sub2api 原生伪装完全一致，不会自相矛盾。
还补不上「站方要的是一个我们不知道的头」这种情况 如果某个站点只认某个私有头，本工具无从推断。此时在 CPA 的 config.yaml 里 给该凭据显式写上 headers，本工具会原样搬过去。这是唯一可靠的途径。

11.1 423 Locked：这不是密钥问题

症状极具误导性 密钥是对的、地址是对的、docker compose ps 一切正常， 但所有管理接口都返回 423。很容易误判成「密钥填错了」而去反复改密钥， 改了也没用。

真因：sub2api 给管理员加了合规确认门禁。管理员没有在面板上确认合规承诺之前， 所有 /api/v1/admin/* 都被中间件直接拦掉，返回 423 Locked + ADMIN_COMPLIANCE_ACK_REQUIRED。 

# 确认是不是这个原因（看 HTTP 状态码）
docker compose run --rm cpa2sub2api python -c "
import tool
s = tool.load_settings()
ok, msg = tool.Sub2Api(s).ping()
print(msg)"

# 修复：用管理员账号登录 sub2api 面板，按提示确认合规承诺。
# 每个管理员各确认一次（确认记录是按 user_id 存的）。

# 命令行确认（可选，把 ID 换成你的管理员 user id）：
docker exec sub2api-postgres psql -U sub2api -d sub2api -c "
SELECT id, email, role FROM users WHERE role='admin';"
本工具会把这个状态翻译成人话 ping() 认出 423 后会直接告诉你「这是合规确认门禁， 不是密钥问题」，并给出处理步骤，不用自己对着状态码猜。
