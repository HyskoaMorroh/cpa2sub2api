CPA2SUB2API 部署与使用教程

把 CPA / CPAMP 生成的 config.yaml 批量灌进 sub2api。 支持全量/单站导入、存量参数修正、模型与优先级、独立 Web 授权面板，以及可选官方 CPA request-relay。

先确认：默认不向上游探测

普通导入可离线分析配置，并调用 sub2api 管理 API。只有总闸开启、站点已授权、且不在永久禁探名单时，才允许向该站发送模型/TLS等检测请求。使用代理或批量开启都不能绕过永久禁探。

MODEL_PROBE_ENABLED=false 只为未保存总闸提供默认关闭；已保存master true/false优先。MODEL_PROBE_HARD_DISABLED=true 是独立硬禁，不能通过保存授权或代理绕过；站授权默认为空。恢复计划默认 0 3 * * 0，按目标调度器时区每周执行。旧半小时任务也需停用或迁移。

一、它做什么，解决什么问题

CPA（CLIProxyAPI）用一份 config.yaml 管理几十到几百个上游凭据； sub2api 是网关，负责真正的调度与计费。两者的账号模型不通用， 手工搬运几百条凭据不现实。本工具就是这条搬运流水线。

按消费者同步受管参数

credentials、priority、concurrency、auto_pause_on_expired、proxy_id、请求头、冷却规则、Websockets、模型白名单等一次性迁移。

保留来源排序

每条凭据的显式 priority 保留顺序与并列关系，再转换为 sub2api 的小值优先；健康分不覆盖来源意图。

健康辅助参数 已核对

已有健康状态用于辅助负载分配，不重新改写显式来源 priority，也不把未检测账号标成可用。

模型与别名保真 已核对

显式模型列表完整保留 name/alias 和后缀；仅未配置列表时，按来源家族执行模型回退。

并发导入

建号 / 探活 / 定价三条链路都走线程池，worker 数可配且自动钳上限。

探测默认关闭

总闸与站授权同时开启才检测，永久禁探站不例外；授权恢复计划改为周频并错峰。

关于 CPA / CPAMP / sub2api 这三个项目都是第三方作品，本工具不修改它们。 本工具校正可由管理 API 控制的字段；第三方网关的选号、重试和协议能力仍受其实际版本限制。

三、Docker 部署

部署模型是「VPS 只拉远程镜像」：本机改代码 → 推 GitHub → GitHub Actions 构建推 Docker Hub / GHCR（以工作流为准） → VPS 拉镜像运行。 所以 VPS 上不需要源码，只需要镜像和几个配置文件。

1拉取镜像

镜像名由你自己的环境变量决定，不是写死的。先在 .env 里设好：

# .env —— 镜像来源
DOCKERHUB_USERNAME=你的DockerHub用户名
DOCKERHUB_IMAGE=cpa2sub2api        # 可选，留空则用仓库名
CPA2SUB2API_IMAGE_TAG=latest       # 可改成已发布的固定SHA标签
cd /opt/deploy
docker compose config --quiet
docker compose pull cpa2sub2api
这一组变量同时决定 CI 往哪里推 GitHub 仓库里 Settings → Secrets and variables → Actions 要配置：
  • Variables：DOCKERHUB_USERNAME（与上面一致）、DOCKERHUB_IMAGE
  • Secrets：DOCKERHUB_TOKEN（Docker Hub 的 Access Token，不要填登录密码）
只配 DOCKERHUB_USERNAME 不配 token 也不会让构建失败 —— 那一处会安静跳过，只发 GHCR。
2准备配置文件

在部署根目录（如 /opt/deploy）放这些文件：

文件作用是否必需

config.yamlCPA / CPAMP 的产物，导入的源数据必需（或用 CPA_BASE_URL 在线拉）

本项目服务通过服务名复用同栈的 mihomo：

    pull_policy: always          # 见下方说明，别用默认的 missing
    container_name: cpa2sub2api
    restart: "no"                # 运维工具，跑完即退

    env_file: [.env]

      SUB2API_ADMIN_KEY: "${SUB2API_ADMIN_KEY:-}"
      CPA_BASE_URL: "${CPA_BASE_URL:-http://cli-proxy-api:8317}"
      CPA_MANAGEMENT_KEY: "${CPA_MANAGEMENT_KEY:-}"
      FALLBACK_PROXY: "${FALLBACK_PROXY:-http://mihomo:7890}"
      SETTINGS_PATH: /app/state/设置.json

      TZ: "Asia/Shanghai"

    volumes:

      - ./config.yaml:/app/config.yaml:ro,z
      - cpa2sub2api-out:/app/out
      - cpa2sub2api-state:/app/state

    # 它持有 sub2api 管理员密钥且能批量建号/改号，收紧权限
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]

    networks:
      - sub2api-network    # 访问 sub2api
      - default            # 访问 mihomo / cli-proxy-api

    depends_on:
      # 只等「起来了」，不等「健康」—— mihomo 节点全挂时会因出不去网
      # 而报 unhealthy，用 service_healthy 会让本工具永远起不来

为什么必须写 pull_policy: always compose 的默认策略是 missing：只看本地有没有同名 tag， 不比对 registry 上的 digest。所以镜像推了新的 :latest， docker compose up -d 也会静默继续用旧镜像 —— 这正是「自动更新不生效」的直接原因。
4启动并自动同步

容器起来就会自动把 config.yaml 同步进 sub2api，跑完即退。 你原来那条命令链加一步即可，不需要额外手动执行任何 py 命令： 

cd /opt/deploy
docker compose config --quiet
docker compose pull cpa2sub2api
docker compose up -d --no-deps --force-recreate cpa2sub2api
docker compose logs --tail 180 cpa2sub2api
docker compose ps -a cpa2sub2api
它是怎么自动跑的 镜像的默认命令是 entrypoint.sh，它执行 一键导入.py（非交互入口）。所以 up -d 启动本容器 = 执行一次同步；配合 restart: "no"，同步完就退出，不会常驻。

以前默认命令是 python tool.py（交互式菜单）， 容器里没有 TTY 就立刻 EOF 退出、什么都不做 —— 看起来 up -d 成功、 实际一次都没同步，必须人工 docker compose run 才有效果。现已改正。

同步是幂等的

重复执行不会重复建号：账号名含内容指纹（sha1(api_key|base_url) 前 8 位）， 已存在的走差异同步，只更新真正变化的字段。默认总闸关闭时不请求上游；每次执行仍会更新受管账号字段，应先检查对照表并保留备份。

配置同步与探活计划要分开

默认 RUN_INTERVAL_SECONDS=0，导入完成即退出。退出码0代表作业完成；退出码非0需排查。配置同步不等于模型探活，不必为了周频探活增加另一个宿主cron或循环。

授权站的恢复计划由 sub2api 调度，默认每周一次。每次修改授权或停用总闸后执行 probes reconcile，核对旧计划已停用或迁移。不要让宿主cron、容器循环、旧半小时计划重复运行。

自动检测还有按规范化主机共享的 604800 秒周预算：正常导入的自动批次与 sub2api 原生周计划共用同一账本，更换 KEY、模型或运行代际不会重新放行。预算在请求前持久化，失败或中断也计入该周；未到期受控跳过，上游请求数为零，不把健康账号改成错误。MODEL_PROBE_CACHE_TTL=604800 只管理结果缓存，缓存过期或最高模型上次失败都不能绕过周预算。显式 diagnose / recover 使用独立手工诊断路径，不占自动周预算，仍逐次核对总闸、站授权和永久禁探规则。

同步会校正已有字段本工具会按当前输入校正受管参数。显式模型列表、alias、排除规则及每条来源 priority 是权威输入；优先级只反向映射为目标数值，不被健康分覆盖。你在 sub2api 手工调整的受管参数可能被同步覆盖；先预览并保留目标数据与私有配置备份。
等待有明确截止计划、恢复、旧账号及健康校准逐项显示进度，等待管理接口时每 5 秒提示一次。每次网络尝试（含写入前校验）最多 30 秒、单阶段最多 10 分钟、整个校准最多 15 分钟；配置中的更短 HTTP 超时仍有效。429 按原 Retry-After 完整暂停，阶段/总截止不重置，最多顺序重试两次且每次重新校验。冷却放不进剩余预算或重试耗尽时明确停止，剩余项未校准；401/403或连续三项真实网络失败也停止。子步骤成功不掩盖整项失败，不能缩短限流冷却或继续向后续账号突发请求。该过程只操作 Sub 管理数据，不额外探活上游。

4.4 HTTP 行为

变量默认说明
HTTP_TIMEOUT30单次请求超时（秒）
HTTP_RETRIES3通用瞬时故障重试次数：连接错误 / 429 / 5xx；管理 API 的 429 按下述独立规则，其余 4xx 不重试
USER_AGENT浏览器 UAsub2api 在 CF 后面时必需

管理 API 返回 429 时，按 Retry-After 的秒数或 HTTP 日期等待；缺失或无效时等待 60 秒，最多额外重试两次。任一次要求等待超过 120 秒就明确失败，不缩短服务器冷却时间。这个管理请求规则不授权任何上游探测。

为什么 User-Agent 要伪装成浏览器 Cloudflare 的「浏览器完整性检查」会按 UA 拦掉一切不像浏览器的客户端， 返回 403 加一行 error code: 1010。 注意这是 CF 边缘直接拒绝、请求根本没到源站，所以在 sub2api 日志里 什么都看不到。鉴权仍然照常校验，这只是让合法的自动化请求不被按 UA 一刀切。

4.5 config.yaml 逐字段说明 新增

这一节回答的是「CPA 的 config.yaml 里每个字段是什么意思、本工具怎么用它」。 与 4.1–4.4 的关系：4.1–4.4 讲的是本工具的配置（.env）， 这一节讲的是输入数据的格式。

先分清两个同名文件 config.yaml 这个名字在本项目里指两样东西，很容易混淆：
· CPA 的 config.yaml —— 输入。CPA / CPAMP 生成的配置，里面有你要导入的全部上游凭据。
· 本项目的 config.yaml.example —— 只是模板示意，不参与运行。
本工具读的是前者，容器里挂在 /app/config.yaml（只读）。

config.yaml 里与本工具相关的顶层段一共 6 个，各自对应 sub2api 的一个渠道：

claude-api-keyanthropicCPA-ClaudeAnthropic Messages

openai-compatibilityopenaiCPA-OpenAI强制 Chat Completions
gemini-api-keygeminiCPA-GeminiGemini 原生

凭据级字段（每个段下面 - 开头的条目）——这些是最需要看明白的：

字段含义本工具怎么处理

alpha-search xAI 搜索能力 迁到 credentials.openai_capabilities（xai 段强制 false）
disabled 该 provider 是否关闭（只在 openai-compatibility 有） 仍做离线分析；默认不探活。只有该站同时通过总闸和站授权且不在永久禁探名单，才可检测并依证据恢复；手工禁用意图应保留
api-key-entries provider 下挂的多个 key（只在 openai-compatibility 有） 每个 entry 展成一条独立账号。 entry 级只有 3 个字段：api-key / weight / proxy-url ——priority 是 provider 级的，所以同一 provider 下的所有 key 共用同一个桶号
rebuild-mid-system-message 把 role=system 的中途消息提到顶层 sub2api 无等价消费者；启用 relay 后由官方 CPA 重建，保留工具与用户内容。未启用时拒绝需要该行为的记录

顶层全局字段按运行消费者分工：直连转换读取调度相关项；relay 额外保留经过合同核准的全局请求行为。

5.5 代理本体：同镜像起两个容器

本项目镜像里已经装了 mihomo 二进制与地理数据，所以 compose 里只需两个服务， 都用同一个镜像，靠 entrypoint 区分角色：

复用已有共享代理 已有父栈通常由 upstream-importer 镜像提供 mihomo-init 与 mihomo。本工具通过服务名访问，不另外起同端口代理。 本镜像也包含初始化脚本、内核和数据，适用于独立部署或替代镜像。具体版本按实际镜像摘要和 mihomo -v 核对，不能沿用旧md5结论。 初始化服务与代理本体必须使用兼容镜像、共享配置卷和同一控制器凭据。
消费方怎么指向这个代理
cli-proxy-api（CPA 本体） config.yaml 里 proxy-url: "http://mihomo:7890"
cpa2sub2api（本项目） FALLBACK_PROXY=${FALLBACK_PROXY:-http://mihomo:7890}
upstream-importer DRIFT_PROXY / MIHOMO_URL，代码回落表也是 http://mihomo:7890

三者都在 default 网络上，靠服务名 mihomo 直连容器 IP， 不经过宿主端口映射 —— 所以宿主端口冲突不影响它们。

宿主 7890 常被占 本机若装着 Clash / Mihomo 客户端，它自己就占着 7890，up -d 会直接 失败（bind: Only one usage of each socket address）。 宿主侧端口是可覆盖的，在 .env 里改： 
# 宿主端口冲突时改这两个（容器内端口不能动）
MIHOMO_HTTP_PORT=7890
MIHOMO_API_PORT=9090
容器内端口必须保持 7890/9090 —— 它要与 config.yaml 里的 proxy-url: http://mihomo:7890 以及 healthcheck.sh 的探测端口一致。改宿主侧即可，容器间通信走服务名，不受影响。 
  mihomo-init:              # 一次性：把配置物化进共享卷
    image: "${MIHOMO_IMAGE:-${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest}"
    pull_policy: always
    restart: "no"
    user: "0:0"             # 卷首次由 Docker 以 root 建出，uid 1000 写不进去
    entrypoint: ["/bin/sh", "/app/mihomo-manager/bootstrap-mihomo.sh"]
    environment:
      MIHOMO_SUB_WOG:  "${MIHOMO_SUB_WOG}"
      MIHOMO_SUB_WOGB: "${MIHOMO_SUB_WOGB}"
      MIHOMO_SECRET:   "${MIHOMO_SECRET:-}"
      MIHOMO_TARGET_DIR: "/root/.config/mihomo"
    volumes:
      - mihomo-data:/root/.config/mihomo:Z

  mihomo:                   # 长驻：同一个镜像，换成 mihomo 本体
    image: "${MIHOMO_IMAGE:-${DOCKERHUB_USERNAME}/${DOCKERHUB_IMAGE:-cpa2sub2api}:latest}"
    pull_policy: always
    container_name: mihomo
    restart: unless-stopped
    user: "0:0"             # 要往配置目录写 cache.db
    entrypoint: ["mihomo"]  # 两个镜像都在 /usr/local/bin，写名字即可
    command: ["-d", "/root/.config/mihomo"]
    depends_on:
      mihomo-init: { condition: service_completed_successfully }
    ports:
      # 宿主侧可覆盖（本机已有代理客户端时会占着 7890）；
      # 容器内端口不能动 —— 要与 proxy-url 和 healthcheck 一致
      - "${MIHOMO_BIND:-127.0.0.1}:${MIHOMO_HTTP_PORT:-7890}:7890"
      - "${MIHOMO_BIND:-127.0.0.1}:${MIHOMO_API_PORT:-9090}:9090"
    volumes:
      - mihomo-data:/root/.config/mihomo:Z
    healthcheck:
      # 见 5.6：脚本不只会判活，还会把出口降级到 DIRECT
      test: ["CMD", "sh", "/root/.config/mihomo/healthcheck.sh"]
      interval: 60s
      timeout: 40s
      retries: 3
      start_period: 40s
三个容易踩的点
  • 两个服务必须挂同一个卷，否则 init 写的配置本体读不到；
  • 两个服务都写 user: "0:0" —— 命名卷首次由 Docker 以 root 建出， uid 1000 往里写会 Permission denied；
  • CentOS 9启用SELinux时，多个服务共享同一config文件使用 :ro,z 共享标签；只给单个容器独占的bind才考虑私有 :Z，不能反复给共享文件重打私有标签。

5.6 出口真的废了会自动降级 容易忽略

机场节点全挂时，mihomo 进程本身活得好好的：端口在听、API 有响应、 AUTO 组里还列着几十个节点名字。日志里看不出任何异常，但所有配了 proxy-url 的上游都会走进这个没有出口的代理里排队到超时 —— 表面现象是上游 502/524。

光把容器标成 unhealthy 救不回来：restart: unless-stopped 不会因为 unhealthy 重启容器，而且健康检查本身改不了选路。 所以健康检查调的是 healthcheck.sh，它会：

  1. 查 9090 API 是否响应（失败使健康检查退出非0；Docker不会仅因unhealthy自动重启）；
  2. 清点 AUTO 组节点数（只用于日志，节点数不是可用性判据）；
  3. 真正经 7890 出一次网。通 → 若当前在 DIRECT 就切回 AUTO；
  4. 不通 → 调 PUT /proxies/PROXY {"name":"DIRECT"} 降级， 再试直连；直连通就保持健康（降级不算失败），都不通才报 unhealthy。
# 手动跑一次（排查用；它真的会切组）
docker compose exec mihomo sh /root/.config/mihomo/healthcheck.sh; echo rc=$?

# 正常时的两种输出：
#   [healthcheck] 出口已恢复（AUTO 组 59 个节点），切回 AUTO
#   [healthcheck] 代理出口不可用（AUTO 节点 59 个，探测 ... 失败），降级 DIRECT
#   [healthcheck] 直连可用，容器保持健康（流量已走 DIRECT）

# 看 compose 记下的最近几次检查结果
docker inspect --format '{{range .State.Health.Log}}exit={{.ExitCode}} {{.Output}}{{"\n"}}{{end}}' mihomo
脚本要在两种基座里都能跑 不同 mihomo 镜像的基座可能不同，本项目镜像是 Debian slim —— 两者可用的命令不同。 Debian 里装了 busybox 也不会自动出现 /usr/bin/nc （实测：have busybox，MISS nc），而切换出口是 PUT，busybox 的 wget 只能发 GET/POST， 必须有 nc。所以脚本对 nc / wget 各做一次"命令探测 + 回退到 busybox <applet>"，同一份脚本两边通用。 两个工具都找不到时它会直接说"本镜像缺工具"，不会伪装成出口故障。

永久禁探规则受保护站点会在规范化的主机名、子域、尾点、代理路径、计划和 TLS 检测中统一拒绝。不要用代理、批量命令或直接改设置文件绕过。

确认要发起检测时，先明确授权站点并保存总闸开启，再检查当前有效状态。MODEL_PROBE_ENABLED=false 不覆盖已保存的true，环境true也不能复活已保存的false。独立硬禁开启时，新增开启操作返回 409 PROBE_HARD_DISABLED，仍可关闭既有授权；需将三个服务的 MODEL_PROBE_HARD_DISABLED=false 统一配置并重建后才能重新开启。正常开启只保存，applyStatus=saved，不校准计划或发模型请求；关闭后仍应确认旧计划停止。

显式TLS对照诊断

diagnose会向指定站发送真实模型测试，仅处理受管、active且schedulable、没有429或临时冷却的账号。必须同时打开总闸和站授权，且不在永久禁探名单。完整原生周检测、恢复和TLS诊断需要已同步、已就绪的安全relay。普通Direct账号先将部署根 .env 的 REQUEST_RELAY_ENABLED=true、REQUEST_RELAY_FORCE_ALL_ACCOUNTS=true 与 COMPOSE_PROFILES=request-relay 设置好，再预览并同步指定站。

# 先按上文设置.env；预览不访问管理端或模型上游
docker compose up -d request-relay
docker compose run --rm cpa2sub2api python tool.py import --preview --host upstream.example
docker compose run --rm cpa2sub2api python tool.py import --yes --host upstream.example
# 已授权站的显式模型请求
docker compose run --rm --no-deps --entrypoint python cpa2sub2api tool.py probes diagnose upstream.example

先测当前真实源传输参数，失败后才试一个明确TLS预设，每账号最多两个模型请求。有效输出、实时授权、账号/来源快照及完整state校验通过，才在 request_relay_learned_tls_profiles 保存绑定来源、KEY、实际模型和consumer二进制摘要的参数，来源或版本变化后旧结果失效。它不试写sub2api账号TLS布尔字段。失败、取消、撤权或并发修改均保留主设置、CURRENT、secrets及其他路由；中断事务由journal恢复。普通导入使用有效学习参数，不隐式诊断；源级成功不代表原生客户端或所有模型兼容。

来源停用、全排除与恢复

显式来源停用或排除全部模型时，账号会原子写为 inactive + schedulable=false，最终模型映射清空，不把内部保护项当作可用模型显示。新建阶段只使用瞬时保护；最终写入与每次重试均核对归属和完整受管字段。

extra.cpa2sub2api_source_disabled 只记录本工具在强来源绑定下设置的停用。已有手工停用、错误、冷却或模型限额不会被推断为本工具停用。来源重新放开后，只有该标记、相同来源、当前停用状态和无错误/冷却/模型限额等条件全部满足，才原子恢复并清除标记；其他运行状态保留。

明确选择账号恢复

普通导入不会复活来源不明的手工inactive或单独 schedulable=false。需要恢复时明确指定你核实过的受管账号ID；这条命令也会向上游发送实际测试，仍受双闸、永久禁探、归属与429/临时冷却约束。

# 示例ID必须替换成你核实过的账号ID
docker compose run --rm --no-deps --entrypoint python cpa2sub2api tool.py probes recover 7 8

自动错误的 error + schedulable=false 也可恢复，但必须明确指定ID、当前源仍启用，且密钥归属和模型映射一致；源映射变化先同步。检测失败不会清错；error 但调度已经开启时会停止并提示核对。不能仅凭另一个KEY成功恢复该账号。

错误恢复分为清错和恢复调度两步，每步及管理429重试前都重新核对授权、来源、代际与状态。未来有效冷却、无法解释的时间或运行状态仍阻断；明确过期的残留可在即时成功后清理。最终读回active、schedulable=true且错误清除才计成功，清错后调度未恢复属于部分完成。

目标管理API没有原子比较并交换条件，前后校验不能消除两个请求之间的全部并发竞态；执行恢复时避免同时手工修改同一账号。

手工账号也要检查原生探测开关本工具对导入账号关闭sub2api的自动费率探测和自动费率同步。实际管理页手工创建第三方账号时，应检查并关闭这两个开关；本工具默认禁探不能替你控制未受管账号的原生任务。

六-A.1、可选 Web：每站开关与批量操作

本工具提供独立授权面板，CLI、交互菜单与 Web 使用相同持久化设置和文件锁。它让你看见每站保存值、当前有效值和永久禁探状态；启动、登录、刷新、开启开关都不向上游发送模型/TLS请求。sub2api 原生管理页不会因此新增这些按钮。

启动并登录

先在私有 .env 填入强随机 PROBE_UI_TOKEN：至少32字符、至少12种不同字符、无空白。仅在登录表单提交令牌，不放进 URL、教程、截图、命令行参数或浏览器持久存储。

PROBE_UI_PORT=8775
PROBE_UI_ORIGIN=http://127.0.0.1:8775
# PROBE_UI_TOKEN 仅在私有 .env 填写强随机值，公开示例不提供令牌
docker compose --profile probe-ui up -d probe-ui
# Docker 本机浏览器打开 http://127.0.0.1:8775

# 远程 VPS：在自己的电脑建立 SSH 隧道（替换用户名与占位域名）
ssh -L 8775:127.0.0.1:8775 user@server.example.invalid

宿主只映射回环 127.0.0.1:8775。改宿主端口时，必须同步把 PROBE_UI_ORIGIN 改为浏览器看见的精确 http(s)://主机:端口 并重建面板；Origin 不含路径，不自动信任 X-Forwarded-*，当前不支持任意反代子路径。

逐站：先看有效状态，再保存

示意中的第一站已有保存授权，但独立硬禁开启，所以当前有效仍为关闭。界面通过 master.hardDisabled 和 master.hardDisableReason 显示具体原因；此时禁用开启控件，允许关闭撤权。MODEL_PROBE_ENABLED 只为未保存master提供默认值，已保存true/false优先；非空 ONLINE_PROBE_HOSTS 继续限制可开启范围。永久禁探站保持独立永久锁。

批量：选择可操作站，再查看保存与应用结果

反馈已经发生下一步
saved授权已保存；开启不会检测核对本次有效状态；需要测试时另用明确命令
applied关闭已保存，管理端计划校准已核实可在 sub2api 查看旧计划状态
saved_not_applied撤权已保存，但计划应用失败或状态再次变化检查管理连接后重试校准，不能当作旧计划已停止

面板开启只保存；关闭会尽力调用管理 API 停用相关旧计划。独立“校准计划”同样只调用管理 API，不是上游可用性检测。CLI 关闭后仍需手动运行 probes reconcile。重建容器后设置由同一 state 卷保留；不要删除该卷。

关闭后的计划校准会逐账号核实。账号较多或管理端返回429时，页面可能等待一个或多个限流窗口；等待期间显示旧列表不代表撤权没有保存。网页请求超过120秒会提示超时，此时先刷新确认保存值和应用结果，避免重复点击。核实 applied 后，才可认为相关旧计划已完成停用校准。

六-B、修正已有账号与清理陈旧账号

正常导入会同步本工具受管账号的现有参数；全部成功后默认自动清理严格受管的陈旧账号，可用 PRUNE_STALE_ACCOUNTS=false 关闭。也可用独立命令先预览再应用。只有完整读取当前配置、所有当前目标均已存在、同步成功且管理标记匹配时，才允许清理；逐候选再次核实并读回删除结果。

docker compose run --rm --no-deps --entrypoint python cpa2sub2api tool.py prune preview
# 检查对照表、计数、所有权标记和失败项后
docker compose run --rm --no-deps --entrypoint python cpa2sub2api tool.py prune apply

分页读取失败、配置损坏、字段合同漂移、导入部分失败或没有严格来源证据时，工具必须停止清理。清理还要求当前 source scope 所有权一致；仅有历史短指纹的 legacy_claim 保留，不自动删除。未知来源旧账号先按明确 ID 强证据认领处理；名称带 ANT- 或备注提到 CPA 都不能单独证明归属。

去重限定在同一来源协议/分组内。同一URL和KEY出现在Codex与OpenAI兼容段时，即使目标平台都为openai，也可能分别走Responses和Chat协议，必须保留各自身份。名称使用稳定来源/分组后缀区分，并迁移可确认受管归属的旧重名账号，不能跨渠道折叠。

六-B.1、request-relay：运行原 CPA 行为

原 CPA 的 cloak、中途 system 重建、请求头、prompt-cache、连接/重试策略与 Responses WebSocket 等行为，需要真正的运行消费者。可选 request-relay 在同一应用镜像内运行从固定官方 CPA 源码构建的 consumer，本项目在诊断出站边界加入禁止重定向的安全补丁，原第三方工作区不修改；镜像包含其 MIT 许可。sub2api 继续负责分组、账号和调度，relay 消费原输入中的相关配置。

consumer来源与原生计划诊断标记

/app/third_party/CLIProxyAPI.PROVENANCE.json 记录固定上游commit、构建镜像、二进制SHA256、构建输入摘要、CGO、Go版本和架构。诊断功能标识为 cpa2sub2api-diagnostic-no-redirect-v1。实际可执行文件与来源记录还必须同时证明整数 automatic_output_cap: 16 和 automatic_output_header: X-CPA2SUB2API-Auto-Output-Cap；只有旧诊断标识的二进制不能就绪。自动请求在 CPA 全部 payload 规则处理后、最后出站前限制输出最多16；压缩、签名、thinking/reasoning 等无法证明小输出的配置受控跳过，不降低选定的真实最高模型。只设置重试为0不能阻止HTTP重定向；诊断分支不跟随30x，relay转换为受控非重定向错误并去掉Location，避免下游再次跟随。普通业务保留原传输行为；手工诊断不使用自动16输出额度，仍遵守诊断分支的禁止重定向和授权检查。

周计划使用 aRID40-hash58 自动标记，显式手工诊断使用 dRID40-hash58；两类新标记都由工具按当前route与实际model摘要生成，固定100个合法ASCII字符，符合当前原生计划DTO的长度上限；旧106字符标记仅为已有state兼容读取保留，不用于新建计划，各自写入精确self-map，完整保留普通和通配模型映射。不要手工拼 dRID/model：Gemini URL模型片段不允许斜线。relay认证后验证当前route/model与全局、站级双闸；自动请求还需匹配当前主机、KEY来源、模型及代际的周预算票据，才选择内部诊断prefix。标记不是需要填入上游配置的真实模型名。

首次启用：开关和 profile 要同时配置

公开模板默认 REQUEST_RELAY_ENABLED=false，保持可直接迁移输入的原行为。若只读预览提示字段需要 relay，默认关闭会明确拒绝该记录，不能把只写备注当成功。

REQUEST_RELAY_ENABLED=true
# 默认false只选择需CPA行为的记录；true也迁移普通Direct受管账号
REQUEST_RELAY_FORCE_ALL_ACCOUNTS=false
COMPOSE_PROFILES=request-relay
REQUEST_RELAY_BASE_URL=http://request-relay:8380
REQUEST_RELAY_STATE_DIR=/app/state/relay
REQUEST_RELAY_SOURCE_SCOPE=default
REQUEST_RELAY_WEIGHTED_BUCKET=false
REQUEST_RELAY_TIMEOUT=600
REQUEST_RELAY_MAX_RESPONSE_BYTES=67108864
REQUEST_RELAY_TLS_PROFILES={}
cd /opt/deploy
# 首次没有私有状态时暂时 unready 正常；不要让导入 depends_on healthy 卡住首次导出
docker compose up -d request-relay
# 此步不会导出私有状态，也不会调用管理端/上游
docker compose run --rm cpa2sub2api python tool.py import --preview
# 此步先导出，等待实际 consumer 代际一致后，才创建/同步账号
docker compose run --rm cpa2sub2api python tool.py import --yes
docker compose ps request-relay
docker compose logs --tail 100 request-relay

服务不映射宿主端口，sub2api 必须能在共同 Docker 网络访问 http://request-relay:8380。派生配置和随机 route/control/consumer 令牌只放在命名 state 卷，不从 Git 或宿主源码目录读取运行派生状态。state 目录绑定一个 scope，保留旧代际用于受控回滚。启动和重载不合成用户请求；新代际先停止接入并排空旧流，默认600秒后取消超时流再切换。

每次官方consumer启动都使用独立的空OAuth目录；旧代际配置和私有令牌保留。正常重启后重新核实服务健康，无需删除state卷；删除该卷会丢失现有路由和控制令牌。

REQUEST_RELAY_FORCE_ALL_ACCOUNTS 默认false，保留普通Direct业务；显式true且relay已启用时，可用 import --preview --host / import --yes --host 迁移指定站，保留身份、优先级和普通模型映射。普通Direct业务与显式单次源探测仍可使用；完整原生诊断需安全relay。

逐 KEY、显式权重池与证据归属

默认业务路径绑定原 KEY，名称、优先级、白名单和来源元数据仍按原配置计算。只有明确设置 REQUEST_RELAY_WEIGHTED_BUCKET=true，才在同 scope、来源类型、分组、原主机内使用权重池。池内另一 KEY 成功只能说明池请求成功，不能当作最初 KEY 的成功证据。

诊断使用 exact-key、零额外重试，并在实际发送前重新核对原站授权；不会借用其他 KEY 证明指定账号可恢复。普通业务仍保留源配置的显式重试策略。未筛出合格模型时保持阻断，不能把空白名单解释为放行所有模型。OpenAI 账号仍采用合法固定 force_responses / force_chat_completions，避免创建后的 auto 探测。

recover 只读加载已有 CURRENT 代际，不重新导出配置或轮换令牌；diagnose 仅在成功事务中保存完整新代际，保留其他路由与现有令牌。发送请求、保存TLS参数及恢复写入前重新核对授权、来源、relay地址、状态目录、权重/账号选择模式和当前代际，中途变化时旧成功结果不能继续使用。遇到不匹配先同步当前来源并核对服务就绪。

显式 TLS 预设与请求代理

fingerprint-profile 是 CPA 请求线形配置，布尔 TLS 开关也不能推出任意主机的 TLS 预设。需要时显式配置精确主机映射：

REQUEST_RELAY_TLS_PROFILES={"upstream.example.invalid":{"impersonate":"chrome136"}}

允许 chrome（当前固定到 chrome136）、chrome136、firefox135、safari184。也可在受管来源条目上写 request-relay-tls，不能写入 api-key-entries 子项：

# 工具扩展；只在目标确实需要、已启用 relay 时配置
claude-api-key:
  - api-key: REPLACE_WITH_PRIVATE_KEY
    base-url: https://upstream.example.invalid
    models:
      - name: claude-sonnet-4-5
        alias: claude-sonnet-4-5
    proxy-url: http://mihomo:7890
    request-relay-tls:
      impersonate: chrome136
      # 可选：容器内绝对可读路径，须自行只读挂载；无需自定义CA时删除
      # ca-bundle: /app/certs/private-ca.pem

目标必须是 HTTPS；未知 preset、冲突 Host、不可读或相对 CA 路径在发布 state 前拒绝。adapter 绑定目标、SNI/Host、每 KEY 认证与显式代理，拒绝重定向，并保持证书及主机名验证。每 KEY/预设隔离连接，环境 NO_PROXY 不会静默绕过已指定代理。

HTTP/SSE 与文本、二进制 WebSocket 使用真实流式传输；只归一化规定的模型协议字段，保留提示词、工具、ID和签名。gzip/deflate 有界解码，Brotli 依赖已安装能力，不支持时明确拒绝。默认解码上限64MiB，可配置1–512MiB，并限制压缩膨胀。畸形压缩会关闭响应，不伪造成功终态。

客户端身份和权限边界TLS 预设或 cloak 参数真实执行，不代表拥有合法 Claude Code 身份、签名、专属分组权限，也不能保证任何站永不封号。上游的账号授权与请求协议仍需按其要求验证。

nginx：保留 Responses WebSocket 与 SSE

下面是客户端到 sub2api 的独立域名反代片段，合并到自己的现有配置；证书路径、服务名和网络均需按实际部署填写。它不把 request-relay 公开到宿主端口。map 在 http 块，location 在自己的 TLS server 块。

# http { ... } 内
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

# 容器 Nginx 与后端在同一 Docker 网络；以下放入已配置证书的 server
# Docker DNS 动态刷新，后端重建换 IP 后无需依赖旧地址
resolver 127.0.0.11 valid=5s ipv6=off;

# API server { ... } 内；示意 server_name api.example.invalid
location /v1/ {
    set $sub2api_backend http://sub2api:8080;
    proxy_pass $sub2api_backend;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
}

# 另一个面板 server { ... } 内；示意 server_name panel.example.invalid
# 此 server 同样配置上面的 resolver；PROBE_UI_ORIGIN=https://panel.example.invalid
location / {
    set $probe_ui_backend http://probe-ui:8775;
    proxy_pass $probe_ui_backend;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
}

保留完整 /v1/responses 路径与 Upgrade/Connection 头，同时关闭 SSE 缓冲。超时应覆盖你的有界请求预算；增大 nginx 超时不能解除 CDN 固定时限。真实验证要分别检查 HTTP Responses、SSE终态、WebSocket升级和续接；仅 nginx -t 或首页200不证明这些协议通过。

Web 授权面板如用独立 HTTPS 域名反代，将 PROBE_UI_ORIGIN 设为浏览器实际 HTTPS 源，并保留 Host。面板无子路径契约；容器 nginx 通过同网络 probe-ui:8775 访问，使用 Docker DNS resolver 与变量形式的 proxy_pass，在面板重建换 IP 后重新解析。变量地址不附加路径，保留原始 URI；若使用固定解析的旧配置，后端重建后须执行 nginx -t && nginx -s reload。宿主 127.0.0.1:8775 和 SSH 隧道入口继续按前文使用。

版本信息、源码缓存与字段合同

import --preview 和显式离线检查不访问 GitHub；预览也不访问管理端或模型上游。公开模板设 FETCH_UPSTREAM_SRC=true，正常线上执行按TTL自动查询官方最新稳定 tag/commit及候选源码，默认每7天；缓存新鲜时不重复HTTP。设 false 则正常执行只用本地证据。镜像内官方 CPA consumer 仍固定版本及摘要，查到新版本不会替换已运行的 consumer 或目标 sub2api。

先检查，再显式取得候选源码

# 当前缓存状态：零网络、零缓存写入
docker compose run --rm cpa2sub2api python tool.py upstream inspect
# 显式刷新已固定版本的源码
docker compose run --rm cpa2sub2api python tool.py upstream refresh
# 已有缓存的离线检查与复用
docker compose run --rm cpa2sub2api python tool.py upstream refresh --offline
# 官方最新稳定版及候选源码；不会自动切换consumer
docker compose run --rm cpa2sub2api python tool.py upstream refresh --latest

默认检查 all；可加 --kind cpa 或 --kind sub2api。--latest 不能与 --offline 同用。官方代码查询不等于上游模型探活，站级探测开关仍默认关闭。

缓存过期与候选漂移如何处理

默认缓存有效期7天，环境变量为 UPSTREAM_CACHE_TTL_SECONDS=604800，对应设置键 upstream_cache_ttl_seconds。源码保存于 out/upstream-cache/<kind>/<commit>/<generation>/manifest.json，每个文件检查 SHA；只有完整代际才更新该 commit 下的 CURRENT.json。最新版本发现报告为 out/upstream-cache/release-evidence.json，固定源码刷新报告为同目录的 source-cache-evidence.json。完整且摘要一致的固定版本缓存过期后可离线复用，但会标记 stale；离线复用不证明当前最新。首次空 out 卷仍可按镜像内固定合同导入，不要求下载Go源码。

未激活的新版本候选不阻止匹配当前固定合同的导入。实际使用的源码发生未审查漂移、出现未知受管字段或旧计划固定身份不匹配时，实际导入和 prune 才会拒绝继续写入或删除。升级时先审查字段及消费语义，适配并固定新 consumer 摘要与基线SHA，再完成真实配置容器、管理页与请求链验证，最后发布已验证镜像。删除候选报告不能让新源码变成兼容源码；没有未审核自动激活任意未来版本的命令。

仅已人工审查并登记、Go AST、完整 token 与编译指令均一致的精确注释/排版源码表示，允许继续采用原字段合同。verified_reviewed_equivalent 描述单个源文件；例如已登记的 CPA v8.0.61 配置结构文件仍采用 v8.0.60 consumer 合同，不会自动升级运行消费者。原始文件 SHA 仍保留在计划与消费前校验中，更换源码后必须重新生成计划；未登记的字节变化、未知字段或语义变化仍需受控复核。

当前受管字段基于已核准的官方 CPA v8.0.60。未知字段、嵌套类型变化和不完整输入必须处理；错误只报告有界字段路径或类别，不回显配置值。其他无关全局字段不被一概否决。

多来源隔离、旧账号修复与显式认领

REQUEST_RELAY_SOURCE_SCOPE=default 是默认稳定来源标识；关闭 relay 时也参与账号所有权。多来源分别使用不同 scope、不同 state_dir/卷和独立配置；不要轮流把两个来源放进同一完整输入来清理。一个 state 目录绑定一个 scope，不能直接改名覆盖其他来源。

  1. 先关闭保存的探测总闸，必要时开启独立硬禁，再备份目标数据及私有配置/state；用新 import --preview 检查字段、来源和范围。
  2. 需要 relay 时同时开关与 profile，先启动服务，再实际导入：原子导出 → 实际 consumer 代际匹配 → 创建/同步。旧格式代际从权威配置重新导出，不手工修改私有清单。

共享代理：节点自动检测与模型探测分别控制

七、工作原理

7.1 优先级是「桶号」，不是权重

CPA 和 sub2api 都按优先级严格分桶：只调度优先级最优的那一桶，同桶内再按负载选号。所以优先级数值不是「权重」，而是「层级」。

7.2 健康辅助与来源排序

来源配置导入路径完整保留每条 priority 的顺序和并列关系，采用全局反向 dense rank 映射。下面的健康评分用于辅助负载参数，不覆盖显式 priority；旧的手工记录兼容入口另有原健康排序行为。

比例的分母：只算「已导入的 KEY」，不算「KEY 总数」

这一条决定了扩容时老域名会不会被无故降级，是实际会踩到的点。

需求文档没有定义分母 原文只写「可调度比例×60% ＋ 活跃比例×40%」。两种取法都符合字面要求， 但只有「已导入数」满足另一条约束：原有的 KEY 和上游不能因为扩容而被降级。
整个域名都是新增时给中位分 0.5 一条都没导入过的域名没有任何实测数据。给 0.5 而不是 0： 既不因「查无记录」被打到队尾（新站可能很好）， 也不凭空排到已验证的健康站前面。对应 load_factor = 4。

7.3 三层容灾链路

7.4 显式模型保真与缺省回退 已核对

先区分显式列表与缺省回退已经配置的 models 是权威输入，完整保留名称、后缀和 name/alias 配对，不因看起来较旧或包含某个词而截断。客户端按 alias 请求；relay 保留该 alias，由 CPA 按原配对选择真正上游模型，不额外暴露未配置的原名。excluded-models 按 alias 匹配。

以下图表只说明没有显式列表时的家族回退，示例型号不代表当前市场最新目录；未检测不能标成实测可用。

# 字段示意：放入你自己的来源条目，不是完整配置
base-url: https://upstream.example.invalid/v1
models:
  - name: vendor-model-v9
    alias: work-model
  - name: vendor-model-v9-extended
    alias: work-model-extended
excluded-models:
  - work-legacy-*

此示例只向客户端暴露 work-model 与 work-model-extended；名字不同的两个 alias 不会被合并。排除规则作用于 alias，真实源模型名由 CPA 消费，不需要为同一个原名额外添加一个未配置的对外身份。

类型规则
gemini只选带 pro 的最高编号，保留该版本全部变体
claude按完整数值版本就高，区分短次版本与日期，保留同版本全部有效档位和后缀
codex单族：GPT整体比较数值版本，只保留最高版本及其全部有效后缀变体
openai多族：GPT、Grok、Claude、Gemini、Kimi及DeepSeek等已识别谱系分别就高，允许多族并存
未识别名称保持原配置语义，不猜测代际或擅自删改
缺省回退中的低档过滤

名字里带 mini / flash / fast 的排除， 只在没有显式模型列表的家族回退路径执行。已经配置的列表与 alias 不会被这组关键词再次筛掉。回退过滤后为空时保持阻断并明确报告，不能把空名单假报成功。

注意 claude 的 haiku 不因档位名称被排除：完整数值版本相同时，opus / sonnet / haiku及其他有效后缀都保留；较低版本仍按就高规则处理。低档关键词判据只认前述三个词。

缺省家族的授权诊断与次新回退

上游声明了 gpt-6 不等于真的能调。模型目录是站方自己填的， 常有「列了但调不通」的情况。开启探测后按代际实发请求验证，据结果分三种处理。

Grok使用动态数值版本比较，保留最高数值版本的全部有效后缀，仍排除 mini、flash、fast。GPT跨主版本作为一个家族比较，不能因为同属一个主版本，就把较低次版本当成最高级的后缀变体。

Kimi K与Moonshot V、DeepSeek V与R分别比较；日期、上下文长度和普通模式后缀不当成更高代际。Claude同时识别已知的档位在前和版本在前形式，日期后缀不作为次版本。未标版本的符号别名及无法识别的名称保留，不猜测其当前指向，也不为凑出“最高”而删除。

仅显式授权时才有模型请求成本

默认关闭时不向上游探测。开启后，默认入口的自动批次与 sub2api 原生周计划按规范化主机共享604800秒周预算；更换KEY、模型或代际不能重新放行。请求前持久化预算，失败或中断也计入该周，未到期受控跳过、上游请求为零，并保持健康账号状态。具体请求数、超时和缓存命中以本轮日志为准。

MODEL_PROBE_CACHE_TTL=604800 管理结果缓存；缓存过期或最高模型上次失败不能绕过自动周预算。显式 diagnose / recover 走手工d标记，不占自动周预算，仍需总闸与站授权，永久禁探站始终拒绝。

同域名不同KEY可能有不同分组或模型权限；一个KEY成功不能证明全部KEY可用，更不能据此恢复未验证账号。

各家族的最新/次新分别检测；只有本轮同KEY、同来源目录和相符代际的成功结果，才能在保留最高版本的同时补入该家族次新。缓存按家族、来源和运行代际区分；旧的次新成功记录不能授权本轮新增次新。

MODEL_PROBE_ENABLED=false      # 未保存master时默认关闭
MODEL_PROBE_HARD_DISABLED=false # true为独立硬禁，三个服务配置一致
ONLINE_PROBE_HOSTS=           # 默认无站授权；非空继续限制可开启范围
MODEL_PROBE_WORKERS=2         # 显式授权后才使用
MODEL_PROBE_CACHE_TTL=604800  # 缓存秒数（7天）
端点拼接必须与 CPA 源码一致

探测用的 URL 按 CPA 自己的拼法构造：baseURL 原样 加各平台端点后缀，不剥离尾部 /v1。CPA 的 base-url 是声明式配置， 末尾的 /v1 是配置的一部分。

段CPA 源码的拼法
claude-api-keybaseURL + "/v1/messages"
codex-api-keyTrimSuffix(baseURL,"/") + "/responses"
openai-compatibilityTrimSuffix(baseURL,"/") + "/chat/completions"
gemini-api-keybaseURL + "/v1beta/models/{model}:generateContent"

按字符串猜测并增删 /v1 可能制造重复版本路径或丢失版本路径，拿到404/HTML。应对照该来源类型的真实协议端点，不能把路径错误当作模型不可用。

判「通」不能只看 200

很多中转站有 catch-all 路由：错误的端点也返回 200，但响应体是 HTML 前端页而不是 LLM 响应。必须校验响应体形态 （id/choices/content 等字段），否则会得到大量假阳性。

400 / 422 只能说明请求被拒绝，不能证明模型可用；应保留参数/协议诊断，不作为恢复成功证据。成功还需符合预期LLM响应结构或有效SSE；目录、HTTP状态和实际模型能力分开判断。

7.5 默认关闭与周频检测

不要发送问候、模型身份询问或周期保活来制造活动。确需检测时，只对你明确授权的站点进行最少必要请求，遵守其使用约定，并使用缓存和周频计划降低重复请求。

关闭授权会协调停用旧计划。请在 sub2api 管理页面核对计划状态和下次执行时间；若旧半小时任务仍在运行，保持总闸关闭并执行 probes reconcile 排查。

8.0 先把日志打开（需求第 8 条）

8.2 只调用高优先级上游，低优先级一次都不试

这是最典型的「看起来在轮循、实际死锁」故障。真实成因是凭据级错误被当成非重试错误：

本工具的对策（已修）：

  1. 域名级冷却：402「预算池耗尽」是整个上游层面的状态 （同一站的所有 KEY 共用同一个池子），不是单个 KEY 的毛病。 本工具给这类错误码下发15分钟、关键词更特异的冷却规则， 避免在同一池子里逐个 KEY 空撞。
  2. 分组内唯一桶号：保证「整桶挂掉才降级」真的能降级。 编号范围是分组内 —— sub2api 选号按 group_id 取候选， 跨分组的桶号之间没有可比性，所以各组都从 10 起。
  3. 桶内冗余：来源配置中同优先级的 KEY 保持并列；一个被冷却后，可尝试同桶的其他合格 KEY。

8.3 报 503 No available accounts 且提示分组权限

这不是本工具的问题 this group only allows Claude Code clients 说明该上游站点只接受 Claude Code 客户端。 需要在 CPA 侧给对应条目配好伪装请求头（user-agent / anthropic-beta / originator）， 与账号本身能否调用无关。

8.4 报 400 invalid codex request

同样与账号无关：该凭据的自定义模型列表里可能含不存在于上游的模型名， 或协议模式（responses / chat_completions）与上游不匹配。 用菜单里的「测试」确认连通性，再看 out/对照表.md 的放行模型是否合理。

8.5 报 524 origin_response_timeout

Cloudflare 的回源超时是 120 秒且无法从源站侧延长 （nginx 的 proxy_read_timeout 对它无效）。 一旦超时 CF 直接返回 524，此时源站其实还在正常重试。 对策是压缩单次请求的上游尝试预算： 

# CPA 的 config.yaml（全局段）
max-retry-credentials: 4     # 12 → 4
max-retry-interval: 2        # 8 → 2

# 最坏耗时 ≈ 4 ×（连接+首字节）+ 3 × 2 秒  ≈ 30 秒以内
# 对 120 秒窗口留足余量

8.6 报 empty or malformed response (HTTP 200) 且 0 个 SSE 事件

流式引导没缓冲的话，网关在还没确认上游会吐 token 时就先提交了 200 OK + text/event-stream 响应头。 此后若上游失败，网关已经没有退路——响应头发出去了，不能改 5xx、 也不能换凭据。唯一结果就是「语法合法但一个事件都没有」的 200。 

# CPA 的 config.yaml
codex:
  stream-bootstrap-buffering: true   # false → true
streaming:
  bootstrap-retries: 3               # 1 → 3

8.10 面板登不上：重置密钥（唯一有效的方法）

// 数据库里已有凭据就直接返回 —— 不再读 secrets 文件

8.11 被自己的 IP 封禁：403 而不是 401

改密钥时很容易触发。CPA 源码里有两个常量：

const maxFailures = 5
const banDuration = 30 * time.Minute

认证失败累计 5 次 → 该 IP 封禁 30 分钟 → 之后所有请求返回 403，包括用对密钥的。

状态码CPA 源码里的含义
401missing management key / invalid management key —— 密钥不对
403IP banned ... / remote management disabled / key not set

只看状态码分不出 403 的具体原因，必须看响应体：

curl -s -i -H "Authorization: Bearer $KEY" \
  http://127.0.0.1:8317/v0/management/get-auth-status | head -20

# 看到这个就是被封了：
#   {"error":"IP banned due to too many failed attempts. Try again in 26m10s"}

解除方法（失败计数在内存里，重启即清空）：

cd /opt/deploy

# 关键顺序：先停 CPAMP，否则它会持续重试、不断延长封禁
docker compose stop cpa-manager-plus
docker compose restart cli-proxy-api
sleep 8

# 确认已解封（应返回 401，而不是 403）
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $(cat secrets/cpa_management_key)" \
  http://127.0.0.1:8317/v0/management/get-auth-status

docker compose start cpa-manager-plus
为什么必须"先停 CPAMP" CPAMP 在后台不断重试连接 CPA。CPA 重启的那十几秒里这些重试全部失败 —— 攒够 5 次立刻又把你封 30 分钟。顺序不能反。

8.12 secret-key 要的是哈希，不是明文

config.yaml 的 remote-management.secret-key 期望 bcrypt 哈希（$2a$10$ 开头，60 字符）。 写明文进去 → 认证彻底失效；哈希不可逆，只能从备份还原。

写哈希前必须校验 这个坑实际踩过：HASH=$(docker compose exec ... python3 ...) 在容器缺 bcrypt 时不会报错，而是把 OCI runtime exec failed... 赋给 HASH。 写进 config.yaml 后认证即失效。 
# 生成后立刻校验，不合格就别往下走
echo "HASH 长度: ${#HASH}"
case "$HASH" in
  \$2*) [ ${#HASH} -ge 59 ] && echo "OK" || echo "长度异常，中止" ;;
  *)    echo "不是 bcrypt 哈希，中止" ;;
esac

8.13 密钥轮换的正确顺序

顺序错了会把自己锁在外面（或触发封禁）。按这个来：

# ① 生成新密钥，直接落文件、不回显（避免进入终端历史）

十、直连与中转不一致：按协议、身份和权限排查

这是需求第 2 条⑴要解决的核心问题，也是实际最常见的「明明能用却报错」： 同一个上游，直接填进 cc-switch 能跑通，经 CPA / sub2api 中转就报 503 No available accounts（有时附带一句 this group only allows ...）。

先分清错误来自哪一层 直连和中转会改变端点、请求体、协议转换、客户端身份头、账号分组和出口。only allows Claude Code clients提示客户端限制；No available channel for model更应核对模型与分组权限。 这些错误不能统一归因于User-Agent。先保存脱敏错误原文、请求阶段和目标类型，再对照直连与中转的差异。

10.1 本工具现在怎么做

原来的实现是纯被动搬运：CPA 的 config.yaml 里写了 headers 就搬过去， 没写就什么都不带。问题在于——靠 CPA 默认伪装跑通的站点，config.yaml 里往往根本没写这些头， 于是导入 sub2api 后请求形态退化，站点就不认了。

现在改为「搬运 + 补缺」：把 CPA 里已有的头原样搬过去， 再把 CPA 没给、但客户端形态必需的头补齐。只补缺，绝不覆盖你显式配的值。

平台补入的客户端头
anthropic
Claude 渠道		 user-agent: claude-cli/2.1.258 (external, cli)、x-app: cli、 anthropic-dangerous-direct-browser-access: true、 x-stainless-* 六项、anthropic-beta

这套头的来源不是拍脑袋 它照抄的是 sub2api 自己内置的客户端伪装常量 （backend/internal/pkg/claude/constants.go 的 DefaultHeaders 与 beta 族）。具体补入值应以目标版本与本次对照表为准；HTTP头一致不代表协议、会话签名或站方专属校验也一致。
还补不上「站方要的是一个我们不知道的头」这种情况 如果某个站点只认某个私有头，本工具无从推断。此时在 CPA 的 config.yaml 里 给该凭据显式写上 headers。直连须遵守目标可消费字段/黑名单；relay由官方CPA消费原头。随后在授权条件下验证实际请求；私有头可能仍不足以满足专属校验。

11.1 423 Locked：这不是密钥问题

症状极具误导性 密钥是对的、地址是对的、docker compose ps 一切正常， 但所有管理接口都返回 423。很容易误判成「密钥填错了」而去反复改密钥， 改了也没用。

真因：sub2api 给管理员加了合规确认门禁。管理员没有在面板上确认合规承诺之前， 所有 /api/v1/admin/* 都被中间件直接拦掉，返回 423 Locked + ADMIN_COMPLIANCE_ACK_REQUIRED。 

# 确认是不是这个原因（看 HTTP 状态码）
docker compose run --rm --no-deps --entrypoint python cpa2sub2api -c "
import tool
s = tool.load_settings()
ok, msg = tool.Sub2Api(s).ping()
print(msg)"

# 修复：用管理员账号登录 sub2api 面板，按提示确认合规承诺。
# 每个管理员各确认一次（确认记录是按 user_id 存的）。

# 命令行确认（可选，把 ID 换成你的管理员 user id）：
docker exec sub2api-postgres psql -U sub2api -d sub2api -c "
SELECT id, email, role FROM users WHERE role='admin';"
本工具会把这个状态翻译成人话 ping() 认出 423 后会直接告诉你「这是合规确认门禁， 不是密钥问题」，并给出处理步骤，不用自己对着状态码猜。
